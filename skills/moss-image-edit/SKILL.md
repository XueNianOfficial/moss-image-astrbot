## 0. 任务与决策流程

参考图编辑是：给模型 1-4 张参考图和一句指令，模型在保留参考图内容的前提下**重绘整幅画面**。这个服务没有蒙版、没有局部重绘，所谓「只改背景」是靠指令约束出来的，不是像素级遮罩，所以任何一次编辑都会轻微改动整张图。理解这一点，就能理解为什么每条指令都必须带「保持不变」的从句。

编辑与文生图共用同一份已加载的权重，编辑只在请求期间挂上编辑 LoRA（底座是 5B 的 MOSS-Image）。冷启动约 20-35 秒，热态 1024²、12 步约 13-15 秒；每多一张参考图都会更慢。

### 0.1 决策流程

1. **判断要不要编辑**：用户指的是「这张图 / 我发的图 / 把它」→ 编辑；没有图，或要的是全新画面 → 走文生图（见 §9）。
2. **定位参考图**：优先当前消息里的图，其次被引用（回复）消息里的图，按 §0.2 的编号规则数好序号。都没有 → 请用户把图片和指令放在同一条消息里发。
3. **分配角色**：单图默认是主体；多图按 §2 指定谁提供身份、谁提供服装、谁提供风格、谁提供场景。
4. **写指令**：改动 + 保留 + 可选氛围，三者齐全（见 §3）。
5. **定参数**：默认 steps 16-20、guidance 4.0、size 留空，试错时 12 步（见 §5）。
6. **调用并交付**：把选择器（`images="1,2"`）和指令一起传给 `moss_edit_image`，成功后用一句话说明改了什么、用了几张参考图（见 §8.4）。

### 0.2 工具契约

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `prompt` | string | 必填 | 编辑指令，必须同时写清改什么、保留什么 |
| `images` | string | 空 | 参考图选择器：逗号分隔的 1 起序号（如 `"1,2"`），也接受 http(s) URL、本地路径、`base64://` 载荷；留空表示用全部可用图片 |
| `size` | string | 空 | 留空则按第 1 张参考图的比例自动决定画布 |
| `steps` | int | -1 | -1 表示用服务端默认（编辑默认 20 步） |
| `seed` | int | -1 | -1 表示随机；复现或对比时传上一次的 seed |
| `negative_prompt` | string | 空 | 追加在全局负面提示词之后 |
| `lora` | string | 空 | 画风 LoRA，`名称:权重`，逗号分隔，叠加在编辑 LoRA 之上；只在用户明确要求某种画风时用 |
| `enhance` | bool | false | 调提示词 skill 重写指令；改图时保持 false |

**参考图编号规则。** 编号先数当前消息里的图（从左到右），再数被引用/回复消息里的图，都从 1 开始，默认最多 4 张。`images` 留空表示「用全部可用图片」；只要消息里的图多于这次编辑需要的张数，就必须显式传选择器（如 `images="1,2"`），不要让无关图片也被当成参考图。选择器里的 URL、路径、`base64://` 同样按出现位置参与编号，但不要把远程 URL 当默认路径——消息里的图最可靠。

`lora` 格式 `名称:权重`，例如 `"film:0.8"`；只有用户明确要求某种画风、且系统提示里列出了对应条目时才填，默认留空。不要为了「提升质量」乱加，它叠加在编辑 LoRA 之上，改变的不只是画风。

`enhance=true` 走的是偏文生图的改写流程，容易把编辑指令扩写成「一张新画面」，改图时默认关闭；只有指令非常口语、需要扩写时才试一次。

### 0.3 先排除三种情况

- 用户只是在聊图、评价图，没有改动意图 → 不要调用工具。
- 用户要求识别、分析、翻译图里的内容 → 这不是编辑。
- 要求超出模型能力（精确文字、多人换脸）→ 先说明限制并给替代方案（见 §1.2、§9）。

## 1. 能力边界

编辑 LoRA 是在 5B 底座上后训练出来的，它擅长「同一主体、换环境或换属性」，不擅长「精确复刻」和「大改结构」。判断一个请求该不该接，看它落在下面哪一栏。

### 1.1 做得好的事

| 类型 | 典型请求 | 成功率 |
|---|---|---|
| 背景替换 | 换海边、换街道、换室内、换纯色棚拍 | 高 |
| 季节与天气 | 秋景转雪景、阴天转晴天、加雨 | 高 |
| 光照与时段时间 | 白天转黄昏、加暖光、改成夜景霓虹 | 高 |
| 服装与配色 | 换外套、换颜色、换材质、加配饰 | 高 |
| 对象增删 | 加一杯咖啡、去掉路人、去掉桌面杂物 | 中高 |
| 视角与景别 | 平视转俯拍、半身转全身、推近拉远 | 中 |
| 整体风格 | 照片转手绘、胶片感、水彩、像素风 | 中高 |
| 姿势微调 | 转头、抬手、换站姿（幅度小） | 中 |

### 1.2 做不好的事

- **文字与字形**：招牌、书页、字幕、包装上的字。模型不具备可靠的字形控制，重试只会得到另一种乱码。
- **精确字符、数字、logo**：不要承诺「把这行字改成 XXX」。需要精确排版或标题 → 改用文生图的 layout 模式（见 §9）。
- **细小结构**：耳环、纽扣、鞋带、栏杆、眼镜框；参考图长边会被缩到 1024，这些细节在编码阶段就已经损失。
- **多人换脸 / 身份替换**：两张脸同时出现时身份会互相污染，换谁都会串。
- **大幅改布局**：从半身改成全身远景、从室内改成完全不同的构图；这更像重新生成，而不是编辑。
- **手指与手部精细动作**：比手势、握持细小物体，容易多指或融合。
- **精确计数与几何**：画面里正好三只鸟、透视线严格对齐，做不到稳定复现。

### 1.3 硬限制（对用户要诚实）

- 底座 5B，编辑 LoRA 只擅长「同主体、变环境/属性」。
- **身份是近似保留**：脸型、发型、气质接近原图，但不是同一个人像素级一致；特写和大头照的相似度明显低于半身/全身。
- 参考图长边缩到 1024，纹理细节有损；输出画布面积约 1024²，比例跟随第 1 张参考图。
- 整图重绘、无蒙版，所以「原图 90% 像素完全不动」做不到。
- 不要对用户承诺「和原图一模一样」「只改这一小块，其他分毫不变」。

## 2. 参考图选择与角色分配

一条消息可能带好几张图，其中只有一部分该当参考图。选错图比写错指令更难救，因为参考图决定了模型眼里的「主体」。

### 2.1 选图优先级

1. 当前消息里的图（按出现顺序）。
2. 被引用/回复消息里的图（编号接在当前消息之后）。
3. 两者都有时，默认用当前消息的图，并问一句确认。

这套编号同时也是 `images` 选择器的编号，选图结果直接写成 `"1,3"` 这样的字符串即可。

不要用这些图做参考：长边小于 512 像素、聊天截图（带界面和气泡）、大面积贴纸或水印遮挡主体、严重压缩的转发图。遇到这类图，直接说「这张图分辨率/遮挡不够，换一张清晰的原图效果会好很多」，不要硬跑。

### 2.2 用几张

| 张数 | 适用场景 | 代价 |
|---|---|---|
| 1 张 | 换背景、换季节、换光照、换服装、加/减物件 | 最快最稳，默认选它 |
| 2 张 | 身份 + 服装、主体 + 场景、内容 + 风格 | 慢 20-40%，成功率仍高，推荐上限 |
| 3 张 | 身份 + 服装 + 场景，每张职责单一 | 明显变慢，属性易串 |
| 4 张 | 极限；只在每张只提供一个属性、指令写得很死时用 | 最慢，失败率高 |

超过 4 张不支持。参考图越多，参考 token 之间的竞争越强，模型越容易把不该混的属性混在一起。能用 1 张解决就不要用 2 张。

### 2.3 角色分配

| 角色 | 通常位置 | 指令里的说法 |
|---|---|---|
| 身份 / 主体 | 第 1 张 | 「第 1 张图里的人物」 |
| 服装 | 第 2 张 | 「第 2 张图的外套」 |
| 风格 / 色调 | 第 2 或第 3 张 | 「参考第 2 张图的色调和笔触」 |
| 背景 / 场景 | 第 3 张 | 「背景用第 3 张图的街道」 |
| 姿态 / 构图 | 第 1 张，或第 4 张 | 「保持第 1 张图的站姿和机位」 |
| 道具 | 第 3 或第 4 张 | 「把第 4 张图的吉他加到手里」 |

第 1 张图同时决定输出画布的长宽比，所以把**主体所在的那张**放第一位。

### 2.4 多图必须点名

反例：「把这两张图融合一下。」——模型不知道谁提供什么，结果通常是两张脸糊在一起。

正例：「以第 1 张图的人物为主体，换上第 2 张图的驼色大衣；保持人物长相、发型和第 1 张图的街道背景不变；第 2 张图只取大衣的颜色和版型，不要它的人脸和背景。」

规则：每张图至少被点名一次，说明「取什么」和「不要什么」。

### 2.5 引用旧图

- 用户回复自己以前发的图并说「改这张」→ 引用消息里的图就是第 1 张参考图。
- 用户回复机器人上一轮的结果 → 同样处理；但注意多轮编辑会累积漂移，超过 2-3 跳就回原图重做（见 §8.3）。
- 同时有新图和引用图 → 问一句「用刚发的这张，还是引用那张？我默认用刚发的」，并给出默认值，不要自己猜。
- 引用消息只带 id、取不到图 → 请用户把图片和指令放在同一条消息里重发。

### 2.6 图文不符时

图里有两个人、用户说「把他衣服换了」→ 追问是哪一个，用方位描述给选项（「左边穿蓝衬衫的，还是右边戴帽子的？」）。不要默认选一个就开跑，改错人比慢更糟。

## 3. 指令写法（编辑语法）

编辑指令是一句**施工说明**，不是画面描述。合格的指令包含三段：改什么、保留什么、可选的氛围补充。缺任何一段，模型就会自由发挥。

### 3.1 三段式模板

```
把<对象/区域>从<现状>改成<目标>；保持<2-4 项>不变；<可选：光线/色调/质感>
```

示例：

- 「把背景从室内白墙换成傍晚的海边；保持人物长相、发型、白色毛衣和站姿不变；晚霞的橙紫色光线打在人物侧脸。」
- 「去掉画面左下角的垃圾桶和纸箱，用路面自然填补；保持街道、店招和行人位置不变。」
- 「把外套换成黑色西装，翻领、深色面料；保持人物长相、发型、站姿和背景不变。」

### 3.2 只改一处

一次调用只做一个语义改动。以下可以合并，因为它们天然耦合：

- 背景 + 光线（换到海边，光线自然要变）
- 服装 + 季节（换冬装，环境也该有寒意）
- 风格 + 色调（转手绘，配色会跟着变）

以下必须拆开：

- 换背景 + 换服装 + 换发型 → 分 2-3 次调用，先做影响面最大的背景。
- 「把 A 改成 B，再把 C 改成 D」且 A、C 无关 → 拆开。

用户一口气提三个要求时，先做第一个并告诉用户「先换背景，满意再换衣服」，不要把所有要求塞进一句。

### 3.3 顺序与具体度

- 把最重要的改动放在句首，保留句紧随其后，氛围放最后。
- 用具体名词、颜色名、材质、数量、位置；删掉「好看一点」「优化一下」「更高级」「有氛围感」这类无法执行的话。
- 长度：单图简单编辑 15-60 字，多图合成 40-100 字。超过 150 字，模型对每个要求的权重都会被稀释。

| 模糊说法 | 改成 |
|---|---|
| 换个好看的背景 | 换成晴天的海边，浅蓝天空、细浪、远处有礁石 |
| 衣服换一下 | 把外套换成米色风衣，长度到膝盖 |
| 加个东西 | 在右手加一杯外带咖啡，纸杯、白色杯盖 |
| 变成晚上 | 改成夜晚，路灯暖光，天空深蓝 |
| 去掉杂物 | 去掉桌面右侧的纸巾和遥控器，用木纹桌面填补 |

### 3.4 命名区域

用「画面方位 + 对象名 + 属性」定位，不要用「这里」「那个」「它」：

- 画面左上、画面右下、前景、背景、中景
- 角色外套、人物右手、头发、鞋子、桌面右侧、窗户玻璃

英文方位词用 top-left、bottom-right、foreground、background、center。

### 3.5 保留句怎么写

列出 2-4 项真正有风险的属性，通常从这五项里挑：**长相（脸）、发型、服装、姿势、构图/背景**。

- 好：「保持人物长相、发型、白色毛衣和站姿不变。」
- 差：「其他全部保持不变。」——空泛，模型无法定位到底哪些不能动。
- 差：一次列 8 项——每条约束都被稀释，等于没写。

换背景时重点保人物；换服装时重点保脸和姿势；改风格时重点保构图和主体位置。

### 3.6 动词选择

| 动词 | 用途 | 强度 |
|---|---|---|
| 换成 / 改成 | 替换已有属性的值（颜色、材质、服装） | 稳，首选 |
| 加上 / 添加 | 新增一个原本没有的对象 | 中 |
| 去掉 / 删掉 | 移除对象，需要说明「用什么填补」 | 中 |
| 替换为 | 整块替换（背景、天空） | 强 |
| 变成 | 状态转换（白天变夜晚、夏变冬） | 强 |
| 调成 | 颜色、亮度、色调微调 | 弱 |

`稍微`、`一点`、`轻微` 会让模型倾向于几乎不改；想要明显改动就别用弱化词。

### 3.7 语言与英文句式

用户用中文就用中文写指令；用户用英文则用英文。中文足以驱动模型，但关键短语可以括注英文一次来降低歧义，例如「背景换成海边（background: sunny beach, soft daylight）」。不要整段翻译两遍，重复描述会让模型在两种说法之间摇摆。

### 3.8 English patterns

模型对英文指令的跟随通常更稳，下面句式可以直接套用：

- `Replace the background with a sunny beach at dusk; keep the person's face, hairstyle, white sweater and pose unchanged.`
- `Change the jacket to a black suit with a clear lapel; keep everything else unchanged.`
- `Remove the trash can and boxes at the bottom left, fill the area with pavement; do not change the street or the signs.`
- `Turn the scene into winter with falling snow; preserve the tree positions, the path and the buildings in the distance.`
- `Use the person from the first image and the outfit from the second image; ignore the face and background of the second image.`
- `Match the color palette and lighting of the second image, keep the composition of the first image.`
- `Add a paper coffee cup to the right hand; keep the hand pose and the sleeve unchanged.`

每条都保持「改动 + 保留」结构；不要写 `make it better`、`improve quality` 这类没有指向的词。

## 4. 多参考图合成

两张以上参考图时，任务从「改一张」变成「按属性拼一张」。核心风险不是画不出来，而是**属性串味**：脸、衣服、背景互相串到不该去的图上。

### 4.1 四种组合模式

| 模式 | 图序 | 指令骨架 |
|---|---|---|
| 身份 + 服装 | 1 人物，2 服装 | 以第 1 张的人物为主体，换上第 2 张的服装；第 2 张只取衣服 |
| 风格迁移 | 1 内容，2 风格 | 保持第 1 张的构图和主体，用第 2 张的画风/色调重绘 |
| 主体 + 场景 | 1 人物，2 背景 | 把第 1 张的人物放进第 2 张的场景；保持人物姿势与长相 |
| 链式编辑 | 1 原图（+2 上一步结果） | 每跳只改一处，逐步逼近目标 |

### 4.2 顺序约定

- 第 1 张：主体/身份，同时决定画布长宽比。
- 第 2 张：服装或风格（只选一个主导属性）。
- 第 3 张：背景或场景。
- 第 4 张：道具、姿态参考这类辅助信息。

### 4.3 防止串味

1. 每张参考图只取 1-2 个属性，并在指令里写明「只取」。
2. 显式排除：「第 2 张图只取外套的颜色和版型，不要它的人脸、发型和背景。」
3. 不要在一句指令里把两张图的全部内容都描述一遍，描述越全，模型越倾向融合。
4. 两张图风格差异极大（照片 vs 插画）时，先决定输出要哪种风格并写出来：「输出为写实照片风格」。
5. 失败信号：脸变成了第 2 张图的人 → 减少参考图数量，或加强「以第 1 张人物为准」的表述。

### 4.4 链式编辑的边界

最多 2-3 跳。每跳只改一处，每跳后检查身份是否还像原图。漂移是累积的：第 3 跳之后通常已经不像原图，这时回原图重做，而不是在漂移结果上继续修。另外工具每轮只取当前消息或引用消息里的图，所以链式需要用户引用上一步的结果图。

### 4.5 成本

2 张参考图约比 1 张慢 20-40%，3-4 张更慢且失败率上升；参考图的 KV 缓存只对同一组图有效，换图就要重新编码。给用户报时按「一张 15-20 秒、每多一张再加几秒」估。

## 5. 采样参数

默认值已经调好，能用默认就不要动。参数出问题时，一次只改一个，并记住上一组值，否则无法归因。

### 5.1 速查表

| 参数 | 默认 | 推荐 | 调整代价 |
|---|---|---|---|
| `steps` | 20（服务端编辑默认） | 12 草稿 / 16-20 成品 | 时间近似线性增加 |
| `guidance_scale` | 4.0 | 3.5-4.5 | 不改时间，改服从度与质感 |
| `shift` | 5.0 | 保持 5.0；4.5 更贴原图，6.0 更大改 | 改变噪声分配，影响结构 |
| `size` | 空（按第 1 张比例） | 留空；必要时显式指定 | 显式值必须 16 的倍数 |
| `seed` | -1（随机） | 复现/对比时固定 | 不改时间 |

### 5.2 steps

- 12 步：快速看构图和方向，细节偏软，适合「先试一版」。
- 16-20 步：成品区间，编辑默认 20。
- 超过 24 步：收益极小，只是变慢；不要在没改指令的情况下靠加步数救画面。
- 改动很细（材质、小物件、文字边缘）时从 20 起步。

### 5.3 guidance_scale（CFG）

- 升高（>4.5）：更听指令、对比更强，但容易过饱和、发硬、出伪影，人物也会变「塑料」。
- 降低（<3.5）：更贴参考图、画面更柔，但可能几乎不改。
- 编辑常用 4.0。判断「太弱」时先升到 4.5，仍不动就改指令，不要继续往 6 以上加。
- 注意：工具签名里没有 guidance 参数，计划中的 `guidance_scale` 是建议/记录值，实际生效值由服务端配置（默认 4.0）决定。想让结果更服从指令，立刻能改的是指令措辞、steps、negative 和参考图选择。

### 5.4 shift

flow-matching 的噪声分配参数，编辑 LoRA 在 5.0 上训练，默认别动。要更贴原图细节试 4.5，要做结构性大改（换季节、换场景类型）可以试 6.0，两者都属实验区。一次只调一档，调完必须对比。

### 5.5 size

留空时服务端按第 1 张参考图的长宽比、约 1024² 的面积算出画布，并对齐到 16 的倍数：1:1 → 1024x1024，3:4 → 约 880x1180，16:9 → 1360x768，9:16 → 768x1360。

显式指定时：宽高必须是 16 的倍数、在 64..2048 之间，且总像素不超过部署配置。比例和参考图差太多时，模型会重排构图而不是简单拉伸——想保留构图就不要改比例。多图时只按第 1 张算比例。

### 5.6 seed

- 复现：把上一次结果里显示的 seed 传回去。
- 对比：固定 seed、只改指令，能看出指令本身的效果；但构图仍可能变，别期待像素级一致。
- 探索：seed 留 -1。
- 不要靠反复换 seed 碰运气来掩盖指令问题，那是浪费几十秒。

### 5.7 成本

热态下 1024²、16 步约 15-20 秒，20 步约 20-25 秒；冷启动额外 20-35 秒；每多一张参考图再加几秒。一次改图对用户就是「等半分钟」，所以先在脑内把指令和参数想清楚，不要拿线上请求做试验。

## 6. 负面提示词

编辑的负面提示词作用在整个画布上，所以原则是**短、稳、不跟参考图打架**。默认值：

```
low quality, blurry, jpeg artifacts, extra limbs, deformed hands, watermark
```

五到七项足够。服务端已配置的全局负面会与你的合并，不要重复写。

### 6.1 什么时候加

| 问题 | 追加 |
|---|---|
| 风格漂移（照片变插画/3D） | `3d render, cgi, anime, illustration` |
| 多余肢体、手指融合 | `extra arms, extra legs, fused fingers, malformed hands` |
| 水印、签名、字幕 | `watermark, signature, text, caption` |
| 过饱和、塑料皮肤 | `oversaturated, plastic skin, harsh contrast` |
| 糊、失焦 | `motion blur, out of focus, low resolution` |

### 6.2 什么时候不要加

- 参考图本身有文字（招牌、海报、书页）→ 不要加 `text`，否则模型会把原图文字擦掉。
- 参考图是夜景/暗调 → 不要加 `dark`、`dim`。
- 人物本来就戴帽子、眼镜 → 不要加 `hat`、`glasses`。
- 参考图本身就是插画 → 不要加 `anime`、`illustration`。
- 永远不要用身份类负面（`different person`、`changed face`）——它会把模型往「改脸」的方向推。
- 超过 10 项后约束互相稀释，甚至反噬；宁可删到 5 项。

## 7. 常见失败与修复

先判断失败类型，再动参数。顺序是：参考图对不对 → 指令有没有「改 + 留」→ 参数是否越界 → 最后才加步数。

| 症状 | 原因 | 修复 |
|---|---|---|
| 背景换了，但人物变了 | 缺保留句 / 参考图太多 / 指令把人物也描述了一遍 | 写死「保持人物长相、发型、姿势不变」；参考图减到 1-2 张；删掉对人物的重复描述 |
| 人物保住了，但指令几乎没生效 | 指令太泛、动词太弱、guidance 偏低 | 具体到颜色/物件/位置；动词换成「换成/改成」；guidance 升到 4.5 |
| 完全忽略参考图，像新生成 | 没指明哪张是主体 / 参考图 3-4 张 / 图本身模糊 | 点名「以第 1 张图的人物为主体」；减到 1 张；换清晰原图 |
| 输出糊、细节软 | 参考图长边不足或压缩严重 / 步数低 | 换原图；steps 18-20；不要靠 guidance 硬拉 |
| 过饱和、风格漂移 | guidance > 5 / 负面没压风格词 | guidance 回 4.0；负面上 `3d render, cgi, anime`（前提是参考图不是这类风格） |
| 文字变成乱码 | 模型没有字形能力 | 不要重试文字；改为不加文字，或走文生图 layout（§9） |
| 肢体错乱、多手 | 姿势改动过大 / 参考图裁在关节处 / 负面缺肢体词 | 缩小姿势改动；换完整构图参考图；加 `extra limbs, fused fingers` |
| 结果像新生成而不是编辑 | 指令写成了画面描述 / 无保留句 / 参考图未生效 | 改成「把 A 改成 B，保留…」；确认参考图在第 1 位 |
| 改动太弱 | 动词太软（「稍微」）/ guidance 低 / 步数低 | guidance +0.5；删掉弱化词；steps 到 20 |
| 改动太强、画面被重画 | guidance > 5 / 指令含「重新设计、换个风格」等大词 | guidance 降到 4.0；缩小改动范围；加 2-3 项保留 |
| 多图属性串味 | 每张图取的属性太多 | 每图只取 1-2 个属性，写明「只取…不要…」 |

修复时一次只改一个变量。连续两次同一症状没有改善，说明是能力边界问题，按 §8 停下来问用户或换路线。

## 8. 迭代与追问

### 8.1 什么时候自动重试

只在失败**可诊断**时自动重试一次，用修正后的指令，最多两次调用：

- 指令缺保留句 → 补上再跑。
- 指令太泛 → 具体化再跑。
- guidance 超出 3.5-4.5 → 回到区间再跑。
- 参考图 ≥3 张且症状像串味 → 减到 2 张再跑。

**不要**自动重试：要求精确文字、要求多人换脸、图本身不可用、用户在做风格探索且每次结果都能接受。这些情况重试只是再花半分钟。

### 8.2 重试怎么改

一次只改一个变量，并记住上一组参数：

- 太弱：指令具体化 + guidance +0.5。
- 太强：缩小改动范围 + guidance -0.5。
- 身份漂移：减参考图 + 强化保留句 + 沿用同一 seed 做对比。
- 没反应：先检查参考图是否真的被用上（是不是第 1 张、是不是清晰）。

### 8.3 跨迭代保持身份

优先「原图 + 累积指令」：始终把原始参考图放第 1 张，指令里把上一轮已经满意的部分写进保留句，而不是拿结果图反复当输入。必须链式时，让用户引用上一步结果作为第 2 张，原图仍在第 1 张。链式不超过 2-3 跳，之后回原图重来，因为二次压缩和重绘会让脸越来越不像。

### 8.4 交付话术

一句话说清「改了什么 + 用了几张参考图」，必要时补 seed：

- 「已把背景换成傍晚的海边，人物和姿势保持不变。想更亮可以说『再亮一点』。」
- 「用第 1 张的人物配了第 2 张的大衣，背景还是原图的街道。」

追问要带默认选项，不要开放式提问：「你想换的是外套颜色还是整套衣服？我默认按外套颜色来做。」

## 9. 与文生图的分工

编辑的优势是保留原图的人、物、构图；一旦这个前提不成立，它就不如直接生成。

### 9.1 判断表

| 信号 | 选择 |
|---|---|
| 用户说「这张图 / 我发的图 / 把它…」 | 编辑 |
| 没有图，或说「画一张 / 来一张」 | 文生图 |
| 要保留脸，但服装、背景、风格全换 | 可以先编辑 1-2 次；不行就转生成 |
| 需要精确文字、排版、标题 | 文生图 layout 模式 |
| 要完全不同的构图或机位，不在乎原图 | 文生图 |
| 多人换脸、身份替换 | 说明做不到，建议生成或换思路 |

### 9.2 把失败的编辑转成生成

1. 把参考图「读」成文字：主体外观、服装、姿势、场景、光线、风格。
2. 按文生图的规范写成提示词（那部分规则归配套提示词 skill 管）。
3. 调 `moss_draw_image`，并明确告诉用户「这次改成重新生成，人物会更接近描述，而不是原图里的那个人」。

不要偷偷换路线。用户以为在编辑，结果拿到一张陌生脸，比直接说明更伤。

### 9.3 与提示词 skill 的边界

编辑指令是句子，不是 tag 堆。不要套用 booru 权重语法（`(word:1.2)`），不要为编辑写长段画面描述，不要把「画质词」堆在句尾。文生图的提示词规范由配套 skill 负责；两者冲突时，编辑场景以本文件为准。

## 10. 输出契约

被要求「给出改图计划」时，只输出一个 JSON 对象，不要 markdown 围栏、不要解释文字、不要注释。

### 10.1 形状

```json
{"prompt": "...", "images": [1], "steps": 16, "guidance_scale": 4.0, "negative": "...", "reason": "..."}
```

### 10.2 字段规则

| 字段 | 规则 |
|---|---|
| `prompt` | 编辑指令，含「改 + 留」；用户用中文就中文，用英文就英文；15-80 字；不含换行 |
| `images` | 1 起的序号，升序，最多 4 个；只列真正要用的；单图可省略（默认 `[1]`），多图必须写；它直接对应工具的同名选择器 |
| `steps` | 整数 12-20；省略表示用默认 20 |
| `guidance_scale` | 数字 3.5-4.5；省略表示 4.0 |
| `negative` | 短字符串，≤10 项；省略表示只用全局默认 |
| `reason` | 一句中文，说明为什么选这些图、这组参数 |

可选键，只在必要时加：

- `size`：仅当画布比例必须不同于第 1 张参考图时，如 `"1360x768"`。
- `seed`：仅当复现或做同 seed 对比时。

不要加其他键，不要嵌套对象，不要写 `"note"`、`"explanation"` 之类的扩展字段。

### 10.3 三个反例

- `"prompt": "一个女孩站在海边，阳光明媚，高清"` —— 这是生成描述，不是编辑；没有保留句，也没有指明改哪里。
- `"images": [2, 1]` —— 顺序错。第 1 位必须是主体参考图，它还决定画布比例。
- `{"prompt": "...", "params": {"steps": 16}}` —— 多余嵌套，违反了扁平结构。

### 10.4 映射到工具调用

`prompt` → `prompt`；`images` → `images`（升序数组用逗号连接，`[1,2]` → `"1,2"`；只有第 1 张时可传 `"1"` 或留空）；`steps` → `steps`（省略传 -1）；`negative` → `negative_prompt`；`size` → `size`（省略传空）；`seed` → `seed`（省略传 -1）。`guidance_scale` 没有对应的工具参数，只是计划级建议，供自检和人工调服务端配置时参考（见 §5.3）；想立刻改变服从度，改指令措辞或 steps。`lora` 不属于计划契约，只有用户点名画风时才在调用时补上。

## 11. 完整示例

以下七个例子覆盖最常见的请求形态。计划里的参数是起点，不是唯一答案；`images` 数组按 §10.4 转成 `"1,2"` 这样的选择器再传给工具。

### 11.1 单图换背景（保身份）

- 用户：「把这张照片的背景换成傍晚的海边，人别变。」
- 可用图片：1 张室内半身照，白光，人物穿白色毛衣。

```json
{"prompt": "把背景换成傍晚的海边，橙紫色晚霞，海面有细浪；保持人物长相、发型、白色毛衣和坐姿不变", "images": [1], "steps": 16, "guidance_scale": 4.0, "negative": "low quality, blurry, extra limbs, watermark", "reason": "单图只改背景，保留句锁到服装层面防止毛衣被重绘"}
```

解释：背景和人物解耦最干净；把毛衣写进保留句，避免换背景时顺手换了衣服。

### 11.2 两张图：人物 + 服装

- 用户发两张图：「让她穿上第二张这件大衣，还站原来的街上。」
- 可用图片：第 1 张街拍女孩，第 2 张驼色大衣商品图。

```json
{"prompt": "以第 1 张图的人物为主体，换上第 2 张图的驼色长大衣；保持人物长相、发型、站姿和第 1 张图的街道背景不变；第 2 张图只取大衣的颜色和版型，不要它的人脸和背景", "images": [1, 2], "steps": 18, "guidance_scale": 4.0, "negative": "extra limbs, deformed hands, product photo text", "reason": "两张图各取所需，显式排除第 2 张的人脸与背景以防串味"}
```

解释：多图编辑必须写「只取什么、不要什么」，否则商品图的人脸会渗进来。

### 11.3 风格迁移

- 用户：「把这张画成吉卜力那种手绘动画风。」
- 可用图片：1 张山湖风景照。

```json
{"prompt": "把整张图转成手绘动画风格，柔和的水彩色块、手绘云层和绿植笔触；保持山脉轮廓、湖面位置和整体构图不变", "images": [1], "steps": 20, "guidance_scale": 4.5, "negative": "photo, photorealistic, 3d render, oversaturated", "reason": "全局风格改动需要更强服从度并压住写实质感"}
```

解释：风格迁移是少数适合把 guidance 提到 4.5 的场景；负面里加 `photo` 只在参考图不是照片时使用（这里要转手绘，所以成立）。

### 11.4 去掉画面里的对象

- 用户：「右边那两个人去掉。」
- 可用图片：1 张街景，右侧远处有两名路人。

```json
{"prompt": "去掉画面右侧远处的两名路人，用路面和橱窗背景自然填补；保持建筑、店招、左侧行人和整体构图不变", "images": [1], "steps": 16, "guidance_scale": 4.0, "negative": "extra people, blurry, low quality", "reason": "移除类必须说明填补方式，否则容易留下模糊色块"}
```

解释：店招上有字，所以不加 `text` 负面，否则招牌文字会被一起擦掉。

### 11.5 季节变化

- 用户：「把这张秋天改成冬天下雪。」
- 可用图片：1 张秋日林荫道，黄叶、草地。

```json
{"prompt": "把画面改成冬天下雪的景象：树枝覆雪、草地和路面有积雪、天空阴沉飘雪；保持树木位置、小路走向和远处建筑不变", "images": [1], "steps": 18, "guidance_scale": 4.0, "negative": "autumn leaves, orange foliage, oversaturated", "reason": "季节变化是全局光照与材质替换，负面需压住残留的秋色"}
```

解释：季节类改动幅度大，保留句要锁住布局而不是细节，否则树的位置会被重排。

### 11.6 失败案例：该追问而不是调用

- 用户发两张自拍：「把这两张合成一下。」
- 可用图片：第 1 张男生自拍，第 2 张女生自拍。

**不要调用工具**，直接问：

> 「你是想把人换到对方身上、换上对方的穿搭，还是把两个人放进同一张图？前两种我按「第 1 张人物 + 第 2 张服装/风格」来做；把两个人放进同一张图属于重新生成，编辑做不到稳定双人合成。你选一个，我立刻开始。」

解释：多图没有角色分配，而且「双人合成」超出编辑能力，先澄清比跑两次错误结果更省时间。

### 11.7 太弱之后的重试

- 上一轮：`"把衣服换成黑色西装"`，结果几乎没变，seed 8241。
- 可用图片：同 1 张半身照。


## 12. 自检清单

调用前逐条过，任何一条不满足就先修，不要开跑。

- [ ] **图对吗**：参考图是当前消息或引用消息里的清晰原图，没有截图、贴纸遮挡、低分辨率？
- [ ] **角色写了吗**：每张参考图在指令里都被点名，说明了取什么、不要什么？
- [ ] **改动明确吗**：指令写清了一个具体改动，用了「换成/去掉/加上」这类可执行动词？
- [ ] **保留句在吗**：列出了 2-4 项真正有风险的属性（脸、发型、服装、姿势、构图）？
- [ ] **只改一处吗**：不相关的要求已经拆成多次调用，没有塞进同一句？
- [ ] **参数正常吗**：steps 12-20、guidance 3.5-4.5、size 是 16 的倍数或留空、seed 只在复现时固定？
- [ ] **负面冲突吗**：没有加会删掉参考图已有内容的词（文字、帽子、暗调、插画风）？
- [ ] **语言一致吗**：指令语种跟用户一致，没有中英两段重复描述？
- [ ] **成本可接受吗**：参考图 ≤2 张（除非确实需要 3-4 张），并已按半分钟量级向用户预期？
- [ ] **交付想好了吗**：准备好一句话说明改了什么、用了几张图，以及下一步建议？
